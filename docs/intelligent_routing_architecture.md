## 0. 一句话与一条红线

**一句话**：用户消息在进入大模型之前，先被一道**确定性级联**筛一遍；某一层能确定地答上来，就直调只读工具、渲染成 markdown 返回，`llmMs = 0`；**任何一层不自信，一律落回 LLM**。

**一条红线**：**漏判免费，误判致命。**

- 漏判（该命中却没命中）＝ 走一次大模型，用户拿到的答案仍然正确，代价只是慢几秒；
- 误判（不该命中却命中了）＝ 用错误的工具短路掉模型，用户**永远拿不到正确答案**，而且没有任何报错。

这条不对称为全系统定调：所有开关默认关、所有词表刻意收窄、所有不确定分支唯一出口是「落回 LLM」。**任何改动若让误判概率上升、哪怕换来大幅提速，都违反本文档。**

## 1. 全链路总图

```
POST /works/:id/chat
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│ 三道闸门（命中即整条落回 LLM，steps 为空）                       │
│   闸门①  讨论态   谈系统/谈任务本身，不是查数据                   │
│   闸门①b 追问态   回指词 + 近窗有 fast-path 结果                 │
│   闸门②  adapter 词门  （逐层生效，见 §3）                        │
│   —— `!` 显式点名豁免①②                                             │
└───────────────────────────────────────────────────────────────┘
        │ 未被拦
        ▼
┌───────────────────────────────────────────────────────────────┐
│ 六个命中位（按序尝试，命中即返回，llmMs = 0）                     │
│   ① 层 P    配置路由        routes.json                          │
│   ② 第 0 层 卡片话术/结构化  manifest scenarios → scenario-routes  │
│   ③ Tier -2 模板直达        manifest route_templates              │
│   ④ Tier -1 提示词配置      patterns.json                        │
│   ⑤ 层 9   多跳计划         plans.json + plan-terminals.json      │
│   ⑥ 第 11 层 显式点名        aliases.json + shortcuts.json         │
│                                                               │
│   （第 12 层「词法召回 → LLM 分类」是**兜底增强**，默认关，        │
│     不占命中位；开与不开都不改变上面六层的语义）                   │
└───────────────────────────────────────────────────────────────┘
        │ 每一层命中后先过
        ▼
┌───────────────────────────────────────────────────────────────┐
│ 只读准入 isRoutableTool                                        │
│   存在 + 可直调 + 显式只读，三者同时成立才派发；                   │
│   不成立 → 该层视为**未命中**（不是错误），继续下游层              │
└───────────────────────────────────────────────────────────────┘
        │
        ├── 全部未命中 ──────────────► siteGate → 第 4 层探索 → streamChat
        │                                                          （探索闭环见 §7）
        └── 命中 → 执行 → 渲染 markdown → SSE 推回（llmMs = 0，回合结束）
                    └ 执行失败 → 按该层声明的 onFailure 走向（见 §5）
```

代码锚点：闸门在 `api-query-router/gates.ts`，级联顺序在 `api-query-router/cascade.ts` 的 `planCascade`，准入在 `router-config/routable.ts`，装配与派发在 `api-query-router/index.ts`，`/chat` 接线在 `server.ts`。

**级联是「规划 + 执行」两段**：`planCascade` 是纯函数，只输出一张「按序尝试的步骤表」，不派发任何工具。这样评测集可以直接断言规划结果，不需要起 HTTP、不需要真工具——这是「误判致命」能被自动化守住的前提。

## 2. 六个命中位：每层六项必答

新增或修改任何一层，下面六项都必须能明确回答；答不上来的那一项，就是这层将来出事的地方。

### 命中位 ①　层 P · 配置路由

| 项 | 内容 |
| --- | --- |
| **触发条件** | 消息**全等**别名，或**包含**关键词（归一化：去全部空白 + 转小写） |
| **参数来源** | 只有静态 `args`，**不从消息里抽参** |
| **渲染方式** | 通用渲染；配置 `render: {type:'schema', schemaId}` 时走声明式表格 |
| **失败后走向** | `stop` —— 已派发过一次就不再往下猜 |
| **急停开关** | 条目 `enabled: false`；整条级联 `WEWORKER_API_QUERY_ROUTE=0` |
| **明确不支持** | 正则、槽位、多跳、从文本抽参、模糊匹配 |

配置：`routes.json`。因为只看「全等 / 包含」，它是六个命中位里**最安全也最钝**的一层——代价是关键词必须写成复合词（`github 仓库列表` 可以，裸词 `github` 不行，见 §8）。

### 命中位 ②　第 0 层 · 卡片话术与结构化直连

三种形态，共用 `scenario-routes.json`（由 adapter manifest 编译，**勿手改**）：

| 形态 | 触发条件 | 额外要求 |
| --- | --- | --- |
| **A · 单工具** | `/chat` body 带 `scenario{adapterId, scenarioId, slots}` | 槽位经 coerce/enum 后**去空白与模板逐字相等**（重建比对门） |
| **A · 多跳** | 同上 + manifest 声明了 `route.plan` | plan 定义存在且 terminal 已登记 |
| **B · 话术** | 消息命中 manifest 卡片话术编译出的锚定正则（± 槽位） | 自由措辞一概不认 |
| **三 · 显式不直连** | manifest 声明 `direct: false` | **只抑制宽泛层**（Tier -1 / 第 12 层），不抑制确定性层 |

| 项 | 内容 |
| --- | --- |
| **参数来源** | 客户端槽位（形态 A）/ 卡片槽位 + `guardNegative`（形态 B）；形态 A 必须过重建比对门 |
| **渲染方式** | 通用；或卡片声明的声明式覆写 |
| **失败后走向** | 形态 A / B 命中后为 `continue + prune:['pattern']` —— **卡片已认领这条消息，失败后不让宽泛正则降级接管**（那会换一个工具作答，比落回 LLM 更糟） |
| **急停开关** | `WEWORKER_SCENARIO_ROUTE=0`；单条卡片 `enabled:false` |
| **明确不支持** | 文本被编辑（漂移）；无 `slotNames`/`promptTemplates` 的旧产物；槽位 coerce 失败；dispatch 鉴权失败后**不降级** |

### 命中位 ③　Tier -2 · manifest 模板直达

| 项 | 内容 |
| --- | --- |
| **触发条件** | 消息 `trim` 后与 `route_templates[]` 模板**锚定全等** `^(?:…)$`（区分大小写） |
| **参数来源** | 枚举槽 `${A\|B\|C}` / 自由槽 `${名}` + `validate` |
| **渲染方式** | 通用 |
| **失败后走向** | `continue`（模板是全等句，失败说明环境问题而非意图问题，允许下游兜） |
| **急停开关** | 模板条目 `enabled:false`；工具被禁用 |
| **明确不支持** | 模糊匹配、大小写不敏感、>4 槽、模板 >120 字符、无槽模板、非 directCapable 工具 |

**顺序位置的两点理由**：逐字全等没有推断成分，所以它排在闸门①之前（再过闸门没有意义）；但它**让位** `!` 显式点名（用户显式指令优先级最高）。

### 命中位 ④　Tier -1 · 提示词配置

| 项 | 内容 |
| --- | --- |
| **触发条件** | 正则或关键词命中，且 `confidence ≥ min_confidence_for_match`（默认 0.8） |
| **参数来源** | `arg_extractors` 抽参 + `default_args` 兜底 |
| **渲染方式** | 通用；覆写走声明式 |
| **失败后走向** | `stop` —— 这是**宽泛层**，命中即已接管，失败就落回 LLM |
| **急停开关** | 条目 `enabled:false`；被卡片 opt-out 抑制 |
| **明确不支持** | `semantic` / `hybrid` 模式（配置里写了会被忽略） |

配置：`patterns.json`。**这一层最容易出事**——它没有 adapter 关键词硬门，正则必须自己把自己收窄。写宽一条，就会越过所有层把别人的话术吃掉。

### 命中位 ⑤　层 9 · 多跳计划（锚点 DAG）

| 项 | 内容 |
| --- | --- |
| **触发条件** | 入口正则应命中 + **不被入口负向命中** + 消息点名了 terminal 的 adapter（闸门②） |
| **参数来源** | 入口静态 args → Anchor Resolver 逐跳产出锚点 → terminal 消费锚点 |
| **渲染方式** | terminal 声明的声明式表格 |
| **失败后走向** | `stop` —— 任一跳歧义 / 未命中 / 鉴权失败 / 用户取消，**整条落回**，不半途换工具 |
| **急停开关** | 计划 `enabled:false`；`!` 前缀豁免闸门② |
| **明确不支持** | 候选超过 5 个（直接落回，不问）；`needs` 引用未产出的锚点（校验期报错） |

配置：`plans.json` + `plan-terminals.json`（入口白名单，编译期/测试期校验用，运行时不读）。

### 命中位 ⑥　第 11 层 · 显式点名与守卫式短路

| 项 | 内容 |
| --- | --- |
| **触发条件** | `!全名 [args]` 显式点名（confidence=1，**豁免所有闸门**）；或 `shortcuts.json` 的正则命中 **且** 消息点名了该 adapter（闸门②） |
| **参数来源** | 条目自带 `extract` 规则 |
| **渲染方式** | 声明式覆写（`schemaId`） |
| **失败后走向** | `stop` |
| **急停开关** | 条目 `enabled:false` |
| **明确不支持** | 别名只支持 JSON 对象参数或「单个必填字符串」启发式 |

**兜底增强 · 第 12 层**（不占命中位，默认关）：词法召回 top-8 且 overlap ≥ 0.08 → 一次 `/v1/messages`（12s、256 tokens）。开关 `WEWORKER_LLM_ROUTE=1` / 设置项 `api_query_llm_route`。**严禁臆造**：LLM 返回的 tool 不在候选内一律判 null。

## 3. 三道闸门

闸门只做一件事：**拦下不该被快捷层接走的句子**。拦错一条真查询的代价只是走一次 LLM（结果仍正确），所以词表刻意只收「明确非查询」的标记。

代码：`api-query-router/gates.ts`。

### 闸门① 讨论态

消息在「谈论/问询系统或任务本身」而非发起查询时命中 → **整条落回 LLM**，任何快捷层都不接。

典型事故句：「这个功能是否正常」（`是否`）、「刚才那个查询失败了」（`失败`）、「这是我常用的归档习惯：先按月分组」（`习惯`）。

**刻意只收明确非查询的词**：查询词（有哪些 / 多少 / 列表 / 到期 …）一律不进此表。

### 闸门①b 追问态

**回指词 且 近窗（最多 3 条 assistant 消息）内有 fast-path 命中记录** → 整条落回 LLM。

为什么需要它：fast-path 回合零 LLM，结果只以渲染 md 落库。紧随其后的追问（「第一条什么状态」）若被宽泛层再次抢中，会**原样重跑同一查询、把追问意图整条吞掉**。落回 LLM 后模型能拿到完整历史并正确接住。

历史读库失败 → 降级为不生效（宁可漏拦，不可误拦）。

### 闸门② adapter 关键词门（逐层生效，非全局）

Tier 0（层 9 / 第 11 层短路）命中但消息里不含该 adapter 的任何指向词 → **该层跳过**，继续下游。防的是「宽泛的 override 正则吃掉没有指向任何站点的口语」。

### 三道闸门共同的豁免：`!` 前缀

`!` 开头是**用户显式点名工具**，属更高优先级指令，豁免①②；若 `!` 开头但没有任何别名匹配，走 `alias_gate` → 清空已规划步骤、整条落回 LLM。**绝不降级到宽泛层猜**——用户明确说了要什么，猜错比不猜糟得多。

> **已知取舍（写在这里防止重复踩）**：闸门① 的词表收的是**高频普通词**，因此会与查询内容撞车。已实例：词表收了 `习惯`（为拦「这是我的归档习惯…」），于是「`微信读书搜索 原子习惯`」这类查询会被整条拦掉。按红线这是**可接受的漏判**（走一次 LLM，答案仍对），但排查「该命中却没命中」时**要先看闸门①**。改词表时同样要权衡：删一个词换取召回，代价是有同类事故句重新漏网。

## 4. 只读准入（isRoutableTool）

任何一个命中位判定命中后，**先过准入才派发**。三个条件同时成立：

1. 工具**存在**于当前工具目录；
2. **可直调**（`directCapable` / `execution.type==='api' && runtime==='background'` / `executionMode==='direct'`）；
3. **显式只读**（`safety === 'read'`，且不要求二次确认）。

不成立时**该层视为未命中**（不是错误、不中止级联），记一条日志后继续下游层。

**为什么写操作绝不进路由面**：路由层是「无确认直发」的通道，用户没有机会在看到副作用之前喊停。写操作必须走模型回合，由模型组织确认。这是准入硬门，不是建议。

## 5. 失败走向语义

每层命中后**必须显式声明**失败走向，没有默认值：

| 走向 | 含义 | 谁在用 |
| --- | --- | --- |
| `{action:'stop', reason}` | 整条落回 LLM，**不再尝试下游层** | 层 P、Tier -1、层 9、第 11 层、第 12 层 |
| `{action:'continue'}` | 继续下游层 | Tier -2 |
| `{action:'continue', prune:[…]}` | 继续下游，但**剪掉指定层** | 第 0 层卡片（`prune:['pattern']`） |

**为什么卡片命中后要剪掉宽泛层**：卡片已经认领了这条消息的意图。它执行失败（工具挂了、鉴权失败），如果此时让 Tier -1 降级接管，宽泛正则会命中一个**别的**工具并把结果端给用户——用户问的是 A，拿到的是 B 的答案，且看不出哪里错了。落回 LLM 至少还能推理出「A 现在查不了」。

**执行期与规划期共用同一判据**（`isLayerSkipped`），保证「规划时说跳过」与「执行时真跳过」不会漂移。

## 6. 短路陷阱与五条防治机制

**短路陷阱**：一条消息被某一层错误认领后，用户**永远无法拿到正确答案**——他不知道自己被路由了，只会觉得「这个助手答得不对」，反复重问也还是被同一层拦下。这是智能路由最危险的失效模式，因为它**静默**。

五条机制共同兜住它：

| # | 机制 | 落点 |
| --- | --- | --- |
| 1 | **不确定即落回**——没有 confidence 门槛的层不允许存在 | 每层的触发条件都要求确定性证据（全等 / 锚定正则 / 关键词包含 / 锚点解析成功） |
| 2 | **输出可识别**——fast-path 结果带路由来源，模型与日志都能看到「这条是谁答的」 | timing 块的 `routeTool`；`label` 字段 |
| 3 | **重问可逃脱**——用户重问时不被同一层再拦一次 | 闸门①b 追问态（回指词 + 近窗 fast-path） |
| 4 | **显式逃生口令**——用户可直接点名工具，绕过所有启发层 | `!别名`，豁免三道闸门 |
| 5 | **以重问率自动探测并降级**——同一工具连续被追问 = 它答不好 | 闸门①b 的近窗计数（超过阈值即整条落回） |

**这五条是安全网，不是免责**。真正的防线是 §8 的防污染校验器：在配置进仓库的那一刻就拦住会引发短路的条目。

## 7. 第 5/6 层的修正：探索是「工具」，不是「路由层」

早期设计把「网站探索 agent」画成级联的第 5/6 层（信息不足时自动去探站点，探到了再回来答）。**现行架构改掉了这个设计。**

### 为什么不做成路由层

1. **路由层的契约是「确定性」，探索的契约是「不确定性」**。级联的每一层都要能回答「命中了吗」；探索的输入常常是「我不知道该不该探」——塞进级联就等于给整条链引入一个敢赌的层，直接违反红线。
2. **探索是高成本动作**（拉起浏览器、可能几十秒）。当成层就是「无条件可能触发」；当成工具就是「LLM 决定要不要付这个成本」。
3. **探索结果的好坏需要判断**。级联只能在「派发/不派发」之间二选一，无法评价探回来的东西对不对；LLM 可以。

### 现行形态：探索是主 LLM 可调用的工具

- **入口**：`siteGate`（第 3 层）判定站点是否已被 adapter 覆盖。未覆盖 **且** 消息含未注册站点 URL → 交给第 4 层执行，作为**兜底的确定性分流**（不是「猜测性路由」）。
- **工具契约**：探索任务对被探索站点**只读**，超时可取消，用户中止即静默取消；默认不放写权限（`WEWORKER_TIER4_ALLOW_WRITES` 才开）。
- **提示词契约**：主 LLM 拿到的工具说明里必须写明「这会在用户机器上打开一个浏览器、耗时数十秒」——让模型有机会选择不探。
- **毕业回流**：同一 host 成功 N 次（默认 3）→ 提示可毕业为新 adapter → 一旦成为 adapter，它就进入上面的六个命中位，**从「探索」变成「确定性」**。

这条修正的意义：**探索闭环的产出不是「一次回答」，而是「一个新的确定性层」**。所有不确定性都被限制在 LLM 回合内，级联本身始终保持确定性。

## 8. 配置的组织：文件 ↔ 层 ↔ 命中位

一个层一个文件，同目录存放；文件内**按 adapter 分节**，便于回答「这个 adapter 配了什么」。

| 文件 | 层 | 命中位 | 分节方式 |
| --- | --- | --- | --- |
| `manifest.json` | — | — | 逐层开关 + schema 版本 |
| `routes.json` | 层 P | ① | `{ "<adapterId>": [条目…] }` |
| `aliases.json` | 第 11 层 | ⑥ | 同上 |
| `shortcuts.json` | 第 11 层 | ⑥ | 同上 |
| `plans.json` | 层 9 | ⑤ | 同上（条目自报 `adapterId`） |
| `patterns.json` | Tier -1 | ④ | `{ "<adapterId>": { "<完整工具名>": 配置 } }`（内层 key 保留完整工具名，归属由校验器强制） |
| `renderers.json` | — | — | 按 `schemaId` 索引（不按 adapter，因为 schema 可跨工具复用） |
| `plan-terminals.json` | 层 9 白名单 | — | 按 adapterId 索引（编译期/测试期校验，运行时不读） |
| `scenario-routes.json` | 第 0 层 | ② | **编译产物，勿手改**（`npm run gen:routes` 生成） |

### 分节的硬规则（曾出过静默事故）

分节**必须嵌在该层自己的字段里面**。两种层的分节写法不同——数组型层分节值是条目数组，
记录型层（`patterns`）分节值是「工具名 → 配置」的对象：

```jsonc
// 数组型：routes / aliases / shortcuts / plans
{ "routes": { "wikipedia.org": [ { "id": "wiki-random", "tool": "wikipedia.org.random" } ] } }

// 记录型：patterns（configs 的两层 key = adapter id → 完整工具名）
{ "configs": { "wikipedia.org": { "wikipedia.org.search": { "patterns": [ … ] } } } }
```

写成下面这样（把分节提到顶层，少了一层嵌套），**加载器会大声报错**：

```jsonc
{ "wikipedia.org": [ { "id": "wiki-random", "tool": "wikipedia.org.random" } ] }
{ "wikipedia.org": { "wikipedia.org.search": { … } } }   // 少了 configs
```

分节归属由校验器强制（工具名前缀去掉最后一段必须逐字等于分节 key），旧形态
（扁平数组 / `configs` 直接以完整工具名为 key）继续可用，两种形态还可以逐条混写。

> 为什么专门为这个写一段：这个形态曾经**静默通过**。各层校验器看到「该层字段缺席」都按「这一层没配条目」放行，于是整层条目全部丢弃、路由悄悄退回 LLM、**没有任何日志**。现在 `adapter-grouped.ts` 的 `misplacedSectionErrors()` 会在加载时认出「看着就是一份 adapter 分节、但位置高了一层」并报错，该层按坏配置回退。配置校验的原则是：**宁可不生效并报错，不可静默不生效。**

### 注释与示例：两者都要，分工不同

- **文件头注释**：给人看的模板、一个完整成功示例、该层常见的写坏方式。解决「怎么填」。
- **条目里的 `examples` 数据字段**：给机器读，是**必填**项。解决「示例可验证」。

`examples` 的三重作用，缺一不可：

1. 给人和 LLM 看——加一条配置时不用去别处翻「这条怎么用」；
2. 给测试读——`shipped-router-config.test.ts` **直接拿它当正例实跑**一遍匹配器，正则/关键词写错当场红，而不是上线后静默不命中；
3. 防污染——**示例就是这条配置的适用边界**，写不出来往往说明这条配置本来就不该加。

**注释里的示例机器读不到，等于写了但没验证**——所以两者不能互相替代。这也消除了「配置在 A 文件、示例在 B 测试文件」的两张皮：正例集从测试文件迁到配置条目，一处维护。

## 9. 防污染：六道闸

「防止添加配置导致路由层被污染」不是靠人自觉，而是六道会自动拦的闸：

| # | 闸 | 拦什么 | 落点 |
| --- | --- | --- | --- |
| 1 | **只读准入** | 写操作、不可直调工具 | `router-config/routable.ts` |
| 2 | **坏配置只回退该层** | 语法/校验错误扩散到全层 | `router-config/loader.ts`（每文件独立校验，失败保留上一份可用配置） |
| 3 | **分节归属校验** | 条目放进别的 adapter 的分节 | `router-config/adapter-grouped.ts` |
| 4 | **词冲突与最短长度** | 一条的匹配词是另一条的子串（工具不同）→ 短的先命中，长的**永远拿不到**；裸词大面积误伤 | `router-config/validate.ts`（`MIN_CONTAINMENT_TERM_LENGTH = 3`） |
| 5 | **正例全覆盖 + 负例零误判** | 配了不生效（引擎未加载导致的假绿）；命中本不该命中的句子 | `api-query-router/__tests__/route-eval.test.ts`（`positiveChecked === routeCount` 断言），正例集由 `shipped-router-config.test.ts` 从配置派生 |
| 6 | **作用域过滤** | 配置引用了当前环境不存在的 adapter | `validate.ts` 的 `isToolInAdapterScope`，被丢条目进 `sources.dropped` |

第 5 道闸里 `positiveChecked === routeCount` 这个断言**不能因为迁移而失效**——它是防止「引擎没被加载、所有层都不命中、测试全绿」的关键保险。

## 10. 维护手册

### 10.1 想做什么，改哪里

| 想做的事 | 改哪里 | 引擎改动 |
| --- | --- | --- |
| 加一条「点名词 → 工具」 | `routes.json` 或 `aliases.json` | 无 |
| 加一条守卫式短路 | `shortcuts.json` | 无 |
| 提升某工具召回 | `patterns.json` 该条加 `examples` 或调 `weight` | 无 |
| 给某工具定制表格 | `renderers.json` 加 schema（并在 `shipped-router-config.test.ts` 登记） | 无 |
| 加一条多跳 | `plans.json` 加 resolver/terminal；从 manifest 进入的还要在 `plan-terminals.json` 登记 | 无 |
| 加一条话术卡片直连 | adapter `manifest.scenarios[].route`，跑 `npm run gen:routes` | 无 |
| 加一条逐字模板 | adapter `manifest.route_templates[]` | 无 |
| 临时下线某条（可逆） | 该条 `enabled: false` | 无 |
| 让工具彻底退出路由面 | 去掉 `directCapable` | 无 |
| 急停整条级联 | `WEWORKER_API_QUERY_ROUTE=0` | 无 |

### 10.2 常见的写坏方式（都会被当场拦下）

| 写法 | 后果 |
| --- | --- |
| 动作词后面不要求分隔符：`(?:搜索)` 直接接捕获组 | 把「搜索引擎」「搜索功能」的「引擎」「功能」当检索词抽走。**动作词后必须跟空白或冒号** |
| 漏写 `negative_patterns` | 讨论态问句（「…怎么用」「…有多少」）被当成查询请求 |
| 关键词用站名裸词（`github`、`v2ex`） | 「帮我在 GitHub 搜索相关仓库」被关键词层吃掉 |
| 抽参正则忘写捕获组 / `arg` 与工具 schema 不符 | 抽不到参数或抽出无效参数 |
| 缺 `examples` | 校验失败，**整个用户层回退**（这是刻意的：写不出示例说明这条还不该加） |
| 同一条关键词被两条不同工具的规则共用 | 校验器报「先命中者赢，另一条永远拿不到」 |
| 分节提到顶层 | 加载器报错、该层回退（见 §8） |

### 10.3 提交前必跑

```bash
cd weworker/backend-ts
npx vitest --run src/api-query-router/__tests__/   # 结构自洽 + 正例全覆盖 + 负例零误判
npm run gen:routes:check                           # 编译产物与 manifest 源一致
npm run route:replay                               # 按用例清单端到端回放
npx tsc --noEmit
```

`route-replay` 把 `docs/router-config-manual-testcases.md` 当作**唯一事实来源**解析，所以不存在「文档与脚本两张皮」。它逐条给出：**是否命中路由**、命中第几层、命中的工具与渲染方式、结果是否正常（行数/字段数/工具报错/落盘指针/空结果）、**耗时**（整条 / 其中路由判定），并附实际输出原文与派发轨迹作为证据。跑完给出汇总：命中 N 条、未命中 M 条（其中**正例却未命中**多少条——那才是要查的），以及最慢的 5 条。

**两层工具，各答一半问题**：

| 工具 | 层次 | 回答什么 | 代价 |
| --- | --- | --- | --- |
| `npm run route:replay` | 引擎级（不碰网络） | 命中第几层、哪个工具、参数对不对、渲染是什么 | 秒级、零 token |
| `node scripts/chat-bench/bench.mjs --router-cases` | 端到端（真实 HTTP+SSE） | 用户**实际拿到什么回答**、整轮多少秒、有没有走路由 | 每条一次真实对话 |

两者读同一份用例清单，所以「引擎判定」与「端到端结果」不会漂移。chat-bench 判「有没有走路由」的依据是 `turn_end` 有没有带 `routeTool` 自描述字段（只有快速路由命中才带），不靠猜。

### 10.4 排查：「这条为什么没命中？」

按这个顺序看，命中率最高的问题排在最前：

1. **闸门① 词表**——消息里有没有 `是否 / 失败 / 习惯 / 怎么 / 是什么 / …吗`？（见 §3 的已知取舍）
2. **闸门①b 追问态**——有回指词，且近窗 3 条 assistant 消息内有 fast-path 命中？
3. **闸门② adapter 词门**——层 9 / 第 11 层命中但消息里没有站点指向词？
4. **只读准入**——工具是否 `safety: 'read'` 且 `directCapable`？
5. **作用域过滤**——adapter 在当前环境里存在且已启用？（看 `sources.dropped`）
6. **本层是否被整层拒了**——看 `sources[].rejected`：既可来自校验不过，也可来自**文件读不懂**（解析失败）。后者以前只打一行 WARN、`rejected` 为空，层静默变空且无从查起；现在两种都记 `rejected`，并且**解析失败同样保留上一份可用配置**，不会让路由表整体变空。

> **第 0 条（先排除）**：如果**所有层同时不命中**，先怀疑「运行中的进程用的不是当前代码」。dev 模式后端是 `tsx src/server.ts` 常驻进程，**热重载只覆盖配置内容，不覆盖引擎代码**——引擎改了必须重启客户端。判据：日志里出现 `router-config parse failed`，或 `GET /sites` 的 `routeEntryCount` 全为 0。

## 11. 新增一个 adapter 的作业流程

五步，全程不需要改引擎代码：

1. **确认工具进得了路由面**：目标工具必须是**可直调 + 显式只读**。写操作到此为止，不要往下走。
2. **从最安全的一层开始**：先加 `routes.json` 的全等/复合关键词条目（带 `examples`）。不要一上来就写 `patterns.json` 正则——那一层没有 adapter 硬门，写宽了会吃掉别人的话术。
3. **跑校验与回放**：`npx vitest --run src/api-query-router/__tests__/` + `npm run route:replay`。红就改配置，不要改测试断言。
4. **按需升级到强层**：需要抽参 → `shortcuts.json`；需要从消息里查库 → `patterns.json`；需要两跳 → `plans.json`（并在 `plan-terminals.json` 登记）。
5. **补一条卡片话术（可选）**：想让客户端卡片点击直达，写进 adapter `manifest.scenarios[].route`，跑 `npm run gen:routes`。

**每一步的准入门槛都是同一条**：能写出一条「应当命中本条」的真实原文（`examples`）。写不出来就说明这条配置的边界还不清楚——**此时正确的动作是不加，让它落回 LLM**。

## 12. 红线

- **只读是准入硬门**：写操作、变更类工具不得进入路由面。
- **不确定即落回**：任何一层不自信，唯一出口是 `return false` 落回 LLM。禁止引入「猜一个试试」的层。
- **漏判免费，误判致命**：任何改动若让误判概率上升，都不接受——哪怕换来大幅提速。
- **内部业务规则不进公开目录**：`weworker/router-config/` 只放随公开基线发布的通用配置；内部规则经 Profile Overlay 与 `WEWORKER_QUERY_ROUTES_CONFIG` 注入。
- **仓库不含真实密钥/账号/内部域名/私网 IP**：示例地址一律 `example.com` / `example.org` / `localhost` / `127.0.0.1`。
- **`scenario-routes.json` 勿手改**：它是编译产物，手改会被下次生成覆盖。要改就改 manifest 再重新生成。
