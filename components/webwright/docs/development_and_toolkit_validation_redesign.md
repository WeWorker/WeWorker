# WeWorker 网站探索开发与 Toolkit 验证工作区改造设计

## 文档状态

- 状态：设计已确认，代码待实现
- 更新时间：2026-08-09
- 适用范围：embedded 网站探索页面的 Toolkit／Tool 工作区
- 改造性质：产品信息架构、前端交互和开发中代码保存能力调整
- 当前实现基线：现有页面仍为「探索｜开发｜调试」三工作区，本设计尚未进入产品代码

本文单独记录开发与调试体验改造方案。实施前应再将已确认规则同步到正式产品／技术设计；本文落盘本身不表示现有代码、API 或其他设计文档已经完成调整。

## 一、结论

页面继续保留三个工作区，但重新定义为：

```text
探索｜开发｜Toolkit 验证
```

原调试工作区按目的拆分：

```text
旧调试工作区
├── development 调试 → 并入开发工作区右侧即时测试面板
└── formal／多 Tool 调试 → 升级为 Toolkit 验证工作区
```

新的完整流程是：

```text
探索
→ 开发与即时测试
→ 应用到 Toolkit
→ Toolkit 正式验证
→ 导出／安装
```

开发阶段的代码修改、Agent 协作、参数测试、失败修复和再次测试全部在同一工作区完成。Toolkit 验证只承担已应用代码和最终产物验证，不再介入开发中的高频反馈循环。

## 二、改造目标与非目标

### 2.1 目标

1. 消除开发和 development 调试之间反复切换工作区的问题。
2. 允许用户手动修改开发中 Python 代码并保存。
3. 保留 Developer Agent 驱动开发，人工修改与 Agent 修改共用同一个开发中版本。
4. 让失败 Debug Run 可以经过用户明确确认后直接成为 Agent 修复证据。
5. 继续使用精确 `code_hash` 控制测试资格和应用资格。
6. 将 Tool 级开发验证与 Toolkit 级正式验证分开。
7. 用「应用到 Toolkit」替换用户界面的「发布」表达。
8. 保持双槽位、正式产物、Debug Run 和导出资格的底层模型不变。

### 2.2 非目标

1. 不提供代码历史、旧开发版本、回滚快照或 Toolkit Revision。
2. 不允许直接编辑已应用到 Toolkit 的代码。
3. 第一版不允许手工修改参数 Schema、返回 Schema 或风险说明。
4. 不自动保存人工代码草稿。
5. 不自动运行测试，不自动调用 Developer Agent，不自动修改代码。
6. 不增加页面操作快捷键，所有主要操作通过明确按钮完成。
7. 不把结构化运行事件描述成原始 Terminal。
8. 第一版不提供原始 `stdout`／`stderr` 实时流、CDP 协议流、网络明细或 Tool 内逐步骤实时截图。
9. 不在本设计中确定 Monaco、CodeMirror 等具体编辑器依赖。

## 三、用户界面术语

底层字段与内部代码可以继续保留 `development`、`formal` 和 `publish`，用户界面统一使用以下文案：

| 内部概念 | 用户界面文案 |
|---|---|
| Development Slot | 当前开发中代码 |
| Formal Slot | 已应用到 Toolkit 的代码 |
| Development Debug Run | 当前修改测试 |
| Formal Debug Run | Toolkit 正式验证 |
| Publish | 应用到 Toolkit |
| Publish Eligible | 已通过测试，可以应用到 Toolkit |
| Formal Validation Status | Toolkit 验证状态 |

固定文案：

- 按钮：`应用到 Toolkit`
- 未验证提示：`当前修改尚未应用到 Toolkit，请先通过测试`
- 成功 Toast：`已成功应用到 Toolkit`
- 代码对照：`当前开发中代码` vs `已应用到 Toolkit 的代码`

「应用到 Toolkit」的准确含义是：将当前开发中实现提升为 Toolkit 当前使用的 Tool 实现，重新生成 Toolkit 正式产物，并清空开发中版本。Tool 对象在创建时已经属于 Toolkit，因此该文案不改变 Tool 的归属关系。

## 四、整体信息架构

```text
全局顶栏
├── WeWorker 网站探索
├── 当前活动状态
├── Agent 浏览器状态
└── 主题切换

页面主体
├── 左侧：Toolkit／Tool 两级导航树
└── 右侧：主工作区
    ├── 工作区 Header
    │   ├── 当前 Toolkit／Tool 上下文
    │   ├── 探索｜开发｜Toolkit 验证
    │   └── Toolkit 验证、导出与安装状态
    └── 工作区 Body
```

### 4.1 工作区排列

工作区固定按产品流程排列：

```text
探索｜开发｜Toolkit 验证
```

- 探索：当前 Tool 作用域。
- 开发：当前 Tool 作用域，包含 development 即时测试。
- Toolkit 验证：当前 Toolkit 作用域，包含 formal 和多 Tool 组合验证。

### 4.2 切换规则

1. 没有选中 Tool 时，「探索」和「开发」不可用；只要存在 Toolkit，「Toolkit 验证」仍可进入。
2. 在探索或开发工作区切换 Tool 时，工作区保持不变并切换到新 Tool。
3. 在 Toolkit 验证工作区切换 Tool 时，仍停留在 Toolkit 验证，并默认选中该 Tool 的验证项。
4. 切换 Toolkit 后，三个工作区都切换到新 Toolkit 上下文；Tool 级工作区选择该 Toolkit 的第一个 Tool。
5. Toolkit 没有 Tool 时，验证工作区显示空态。
6. 全局活动状态点击后，应跳转到实际承载该活动的工作区：Exploration 跳到探索，Development Run 和 development Debug 跳到开发，formal／组合验证跳到 Toolkit 验证。

## 五、探索工作区

探索工作区保持当前 Tool 作用域和现有主要能力：

- 新建 Exploration。
- 查看 Agent 步骤、执行动作、页面观察和最终结果。
- Follow-up、暂停、人工接管、取消和回放。
- 查看探索历史。
- 选择一次成功 Exploration 作为开发依据。

探索是证据采集阶段，不与开发工作台合并。一次开发周期仍最多选择一次完整成功 Exploration，普通继续开发期间不能更换来源 Exploration。

## 六、开发工作区整体布局

开发工作区采用左侧核心开发区 `60%` 加右侧即时测试面板 `40%` 的响应式布局：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ Tool 名称与状态  [查看 Tool 定义]  当前修改状态  [应用到 Toolkit] [重新开始 ▾] │
├───────────────────────────────────────┬──────────────────────────────────────┤
│ 左侧：代码与 Agent 协作区              │ 右侧：即时测试面板                    │
│                                       │                                      │
│ 当前开发中｜已应用代码｜代码对照         │ 当前开发中代码｜已应用到 Toolkit 的代码 │
│                                       │                                      │
│ 代码编辑器                             │ 参数表单                              │
│                                       │                                      │
│ 保存修改／取消修改                     │ 运行测试／取消运行                     │
│                                       │                                      │
│ 当前开发依据                           │ 结构化运行详情                         │
│ Developer Agent 指令框                 │ 结果、错误、截图和日志                 │
│ 提交给 Developer Agent                │ 作为修复依据                           │
└───────────────────────────────────────┴──────────────────────────────────────┘
```

### 6.1 开发工作区 Header

Header 展示：

- Tool 名称和简短功能描述。
- 「查看 Tool 定义」按钮。
- 当前修改状态。
- 「应用到 Toolkit」按钮。
- 「重新开始」菜单。

「查看 Tool 定义」打开只读抽屉，展示功能描述、起始 URL、运行后页面效果、所属 Toolkit、来源 Exploration 和当前开发依据。抽屉只能通过明确关闭按钮关闭。

当前修改状态：

| 条件 | 状态文案 |
|---|---|
| 没有开发中版本 | 当前无待应用修改 |
| 存在未保存草稿 | 有未保存修改 |
| 已保存但当前哈希没有成功测试 | 当前修改待测试 |
| 正在测试 | 正在测试当前修改 |
| 当前哈希测试失败 | 当前修改测试失败 |
| 当前哈希测试成功 | 当前修改已通过测试 |
| 正在应用 | 正在应用到 Toolkit |

### 6.2 左侧代码视图

代码区提供三个视图：

```text
当前开发中代码｜已应用到 Toolkit 的代码｜代码对照
```

规则：

1. 「当前开发中代码」允许进入编辑状态。
2. 「已应用到 Toolkit 的代码」始终只读。
3. 「代码对照」只计算当前两个槽位的临时 Diff，不产生历史版本。
4. 没有已应用版本时，代码对照不可用。
5. 没有开发中版本但存在已应用版本时，默认展示已应用代码，并提供「基于已应用代码开始修改」。
6. 人工编辑只修改当前开发中代码，不直接修改 Schema 和运行契约。

代码编辑器的产品能力：

- Python 语法高亮。
- 行号。
- 搜索。
- 基础错误定位。
- 未保存状态提示。
- 「保存修改」和「取消修改」。

具体编辑器实现应在编码前检查现有依赖；如需新增依赖，应单独说明原因并获得确认。

### 6.3 手动编辑与保存

点击「编辑代码」进入编辑状态，显示：

```text
保存修改｜取消修改
```

保存规则：

1. 只允许保存到当前开发中版本。
2. 请求携带进入编辑时的 `expected_code_hash`。
3. 服务端比对哈希，防止覆盖 Developer Agent 刚生成的新版本。
4. 服务端复用现有 Python AST、函数名、参数与 Schema 一致性校验。
5. 保存时保留来源 Exploration、正式版本基线和 Debug Run 证据等槽位元数据。
6. 保存成功后重新计算 `code_hash`，当前修改立即变为未验证。
7. 如果用户改变函数参数签名并导致现有 Schema 不一致，保存失败并显示准确错误。
8. Agent、Debug 或其他全局互斥活动运行期间禁止保存。
9. 不提供自动保存。

存在未保存草稿时：

- 禁止运行当前开发中代码。
- 禁止提交 Developer Agent 指令。
- 切换 Tool、工作区或离开页面前要求用户明确保存或放弃。
- 草稿只存在前端内存，不持久化到本地存储或服务端。

### 6.4 Developer Agent 协作

Agent 输入区展示当前明确选择的开发依据：

```text
来源 Exploration #...
基于已应用代码 sha256:...
修复依据 Debug Run #...
```

用户填写自然语言修改指令后，点击：

```text
提交给 Developer Agent
```

提交前必须满足：

- 没有未保存人工草稿。
- 没有冲突的全局活动。
- Debug Run 证据已经由用户明确选择。
- 当前开发中版本没有被其他写入覆盖。

Agent 成功后直接覆盖当前开发中版本，生成新 `code_hash`，右侧参数表单根据新 Schema 重新渲染，当前修改回到「待测试」。系统不自动运行测试。

### 6.5 Debug Run 证据绑定

系统可以推荐刚刚失败且属于当前 Tool 的 Debug Run，但不能静默绑定，也不能自动调用 Agent。

当前代码测试失败后显示：

```text
检测到当前代码的失败运行 #debug-run-892
TimeoutError: Waiting for selector '#submit'

[作为修复依据] [查看详情]
```

点击「作为修复依据」后：

1. 校验 Run 属于当前 Toolkit 和 Tool。
2. 校验 Run 渠道和对应 `code_hash`。
3. 在左侧输入框上方增加 Evidence Chip。
4. 聚焦 Developer Agent 输入框。
5. 等待用户补充指令并明确提交。

如果 Run 对应旧代码哈希，Evidence Chip 必须标注「来自旧代码版本」。

提供给 Agent 的 Debug Run 证据应经过脱敏，只包含必要的输入参数、错误摘要、结构化结果、执行前后 URL／标题、代码哈希、日志摘要和截图引用信息；不得包含 `target_id`、`cdp_url`、API Key、模型配置、环境变量或用户本机绝对路径。

### 6.6 重新开始菜单

根据当前状态展示：

```text
基于已应用到 Toolkit 的代码重新开始
从 Exploration 重新开发
放弃当前开发中代码
```

所有会覆盖或清空开发中版本的操作必须通过明确确认弹窗，说明当前修改不可恢复。已应用到 Toolkit 的代码不受影响。

## 七、右侧即时测试面板

### 7.1 测试渠道

测试渠道为：

```text
当前开发中代码｜已应用到 Toolkit 的代码
```

开发工作区默认测试当前开发中代码。已应用代码渠道主要用于对照和快速确认；决定 Toolkit 导出资格的正式验证仍在 Toolkit 验证工作区完成。

不存在的渠道保持禁用，不自动创建任何槽位。

### 7.2 参数表单

根据当前测试渠道对应的 `parameters_schema` 渲染：

- `string`：文本输入。
- `integer`／`number`：数字输入。
- `boolean`：复选框。
- 必填字段：明确标记。
- `description`：辅助说明。
- `default`：初始值。

前端只做即时提示，最终校验由服务端完成。第一版只在当前页面会话中保留最近一次输入，不提供持久化参数模板，避免无意保存敏感业务参数。

### 7.3 运行控制

主要操作：

```text
运行测试
取消运行
再次运行
```

规则：

1. 存在未保存代码时禁止运行当前开发中版本。
2. Debug Run 固定记录本次执行的 `code_hash`。
3. 已应用代码测试额外记录当前正式产物哈希。
4. 参数仍由服务端复核。
5. Debug Run 和 Developer Agent 继续遵守全局活动互斥。
6. 不提供运行快捷键。

### 7.4 运行详情

面板名称固定为「运行详情」，不称为 Terminal。

第一版展示：

- Run 已创建。
- Runtime 已启动。
- 当前 Tool 和参数摘要。
- 运行中。
- 成功、失败或取消。
- 结构化业务结果。
- 错误摘要。
- 执行前后 URL／标题。
- 最终截图。
- 已保存的 `process.log` 入口。
- 存在时显示异常详情入口。

第一版不承诺原始 stdout／stderr、网络事件、CDP 报文、实时 Traceback 或 Tool 内逐步骤截图。若后续需要实时日志，必须单独设计增量日志接口和脱敏规则。

## 八、应用到 Toolkit

### 8.1 解锁条件

「应用到 Toolkit」只在以下条件全部满足时启用：

1. 存在开发中版本。
2. 没有未保存人工草稿。
3. 当前开发中 `code_hash` 存在成功的 development Debug Run。
4. 没有冲突的全局活动。
5. 点击后服务端复核期间，开发中版本没有发生变化。

未满足测试条件时显示：

> 当前修改尚未应用到 Toolkit，请先通过测试

### 8.2 应用行为

点击「应用到 Toolkit」后：

1. 服务端重新读取当前开发中版本。
2. 精确匹配成功 Debug Run 的 `code_hash`。
3. 生成并校验 Toolkit 正式产物。
4. 将当前开发中版本提升为 Toolkit 当前版本。
5. 清空开发中槽位。
6. 重新计算 Toolkit 正式产物哈希。
7. 返回新的 Toolkit 验证状态。

成功 Toast：

> 已成功应用到 Toolkit

应用成功后开发工作区显示「当前无待应用修改」，默认展示已应用代码，并提供「前往 Toolkit 验证」。页面不强制自动切换工作区。

由于 Toolkit 正式产物哈希可能随任一 Tool 的应用而改变，系统必须重新计算 Toolkit 下全部 Tool 的正式验证资格。旧 formal Debug Run 只有同时匹配当前 Tool 代码哈希和当前正式产物哈希时才继续构成有效证据。

## 九、Toolkit 验证工作区

### 9.1 作用域与目标

Toolkit 验证工作区属于当前 Toolkit，不属于单个 Tool。它负责验证已应用到 Toolkit 的真实产物，并决定导出和安装资格。

主要内容：

```text
Toolkit 验证
├── Tool 正式验证矩阵
├── 单 Tool 已应用代码验证
├── 多 Tool 固定顺序组合验证
├── 正式产物哈希与验证状态
└── 导出／安装资格
```

### 9.2 Tool 验证矩阵

矩阵至少展示：

- Tool 名称。
- 已应用代码哈希。
- 当前正式产物哈希。
- 未验证／验证中／成功／失败状态。
- 最近一次 formal Debug Run。
- 是否匹配当前正式产物。

状态示例：

```text
Tool A    已验证
Tool B    待验证
Tool C    验证失败
```

点击某一 Tool 后，在同一工作区打开参数表单和运行详情，不切回开发工作区。

### 9.3 单 Tool 正式验证

正式验证必须实际运行 Toolkit 当前正式产物，不得绕过正式 CLI 直接执行 `formal.json`。

验证成功后：

- 更新该 Tool 对当前代码哈希和正式产物哈希的验证证据。
- 刷新 Toolkit 验证 `X/Y`。
- 全部正式 Tool 验证通过后解锁导出和安装。

验证失败后提供：

```text
[基于此结果继续修改] [查看详情] [再次验证]
```

点击「基于此结果继续修改」后：

1. 切换到当前 Tool 的开发工作区。
2. 如果不存在开发中版本，先基于已应用代码创建开发中版本。
3. 将该 formal Debug Run 作为明确选择的修复依据。
4. 聚焦 Developer Agent 输入框。
5. 不自动修改代码，不自动提交 Agent。

这次切换发生在正式交付验证失败后，表示开始新的开发周期，不属于开发中修改与测试的高频往返。

### 9.4 多 Tool 组合验证

同一 Toolkit 下的 Tool 按用户明确配置的固定顺序执行，共享 Toolkit Runtime Store，并持续操作同一浏览器页面。

组合验证必须展示：

- Tool 顺序。
- 每个 Tool 的参数。
- 当前执行位置。
- 每一步成功／失败状态。
- 失败后停止规则。
- 组合运行的最终结果和日志。

多 Tool 组合验证的后端领域对象和 API 由对应技术设计单独确定；本设计只确定其归属 Toolkit 验证工作区，不将其放回 Tool 开发工作区。

### 9.5 导出与安装

只有当前 Toolkit 下全部正式 Tool 都针对当前正式产物哈希验证成功时，才允许：

- 导出 Toolkit。
- 安装到 WeWorker。

禁用状态必须说明具体未验证或失败的 Tool。导出和安装继续由服务端最终复核，前端状态不是安全边界。

## 十、关键业务流程

### 10.1 首次开发

```text
创建 Toolkit 和 Tool
→ 完成一次成功 Exploration
→ 选为开发依据
→ Developer Agent 生成开发中代码
→ 在开发工作区右侧运行测试
→ 测试成功
→ 应用到 Toolkit
→ 进入 Toolkit 验证
→ 正式产物验证成功
```

### 10.2 人工修改

```text
编辑当前开发中代码
→ 保存修改
→ 生成新 code_hash
→ 当前修改回到未验证
→ 运行测试
→ 测试成功后应用到 Toolkit
```

### 10.3 Agent 修复

```text
当前代码测试失败
→ 点击「作为修复依据」
→ 补充自然语言修改要求
→ 提交给 Developer Agent
→ Agent 覆盖开发中代码
→ 用户再次运行测试
```

### 10.4 应用后验证失败

```text
Toolkit 正式验证失败
→ 点击「基于此结果继续修改」
→ 基于已应用代码创建开发中版本
→ formal Debug Run 成为修复依据
→ 用户提交修改要求或手动编辑
→ 重新测试并再次应用到 Toolkit
```

## 十一、状态与一致性规则

### 11.1 测试资格绑定

- 成功 Debug Run 必须精确匹配当前开发中 `code_hash`。
- 人工保存或 Agent 修改后产生新哈希，旧成功 Run 立即失去应用资格。
- 旧 Run 仍可查看和作为显式历史证据，但必须标注代码版本不一致。

### 11.2 写入冲突

- 人工保存携带 `expected_code_hash`。
- Developer Agent 完成写入时继续通过服务端槽位锁保护。
- 人工编辑、Agent 写入和应用到 Toolkit 不得静默互相覆盖。
- 哈希冲突时保留服务端最新版本，并要求用户重新加载后处理本地草稿。

### 11.3 全局活动互斥

- Exploration、Development Run、Debug Run 和 Toolkit 组合验证继续遵守现有全局互斥规则。
- 活动运行期间禁用冲突的保存、提交、测试、应用、导出和安装操作。
- 禁用原因必须可见。

## 十二、API 与数据影响

### 12.1 新增人工保存接口

计划新增：

```http
PUT /api/toolkits/{toolkit_id}/tools/{tool_id}/development
```

请求：

```json
{
  "code": "...",
  "expected_code_hash": "sha256:..."
}
```

服务端处理：

1. 确认开发中版本存在。
2. 确认没有冲突活动。
3. 比对期望哈希。
4. 保留 Slot 的其他字段。
5. 复用现有 Slot 校验。
6. 原子覆盖开发中版本。
7. 返回新代码哈希和未验证状态。

### 12.2 复用现有接口

- development Debug Run 继续复用当前 Debug Run 创建、取消、列表和详情接口。
- Developer Agent 继续复用 Development Run 接口。
- 「应用到 Toolkit」前端可继续调用现有 publish API；内部路径和函数名不要求随用户文案同步重命名。
- Toolkit 正式验证继续复用 formal Debug Run 和 export status 能力。

### 12.3 不增加的数据

- 不增加代码版本表。
- 不保存人工代码草稿。
- 不保存 Diff 结果。
- 不复制 Debug Run 的完整代码快照。
- 不改变正式产物和 Toolkit Runtime Store 的现有边界。

## 十三、前端结构影响

实施时建议：

1. 保留探索视图。
2. 将当前开发视图升级为双栏开发工作台。
3. 把现有 development Debug UI 拆为可嵌入开发工作区的即时测试组件。
4. 将现有 formal Debug UI 和后续多 Tool 组合验证收口为 Toolkit 验证视图。
5. 工作区状态由 `explore | develop | debug` 调整为 `explore | develop | validate`。
6. 草稿、代码视图、测试渠道和参数输入按 Toolkit／Tool 隔离。
7. 现有内部 API 命名可以保留，前端适配层对用户文案做映射。

不得在没有检查项目现有依赖和获得确认的情况下增加 Monaco、CodeMirror 或新的前端框架。

## 十四、响应式设计

### 14.1 主工作区宽度 `>= 1100px`

- 开发工作区使用双栏。
- 默认 `60%／40%`。
- 允许拖动分隔条。
- 左侧最小宽度 `620px`。
- 右侧最小宽度 `420px`。

### 14.2 `800px～1099px`

- 左侧代码与 Agent 区作为主体。
- 右侧即时测试改为可固定的侧边抽屉。
- 运行期间允许保持抽屉展开。

### 14.3 `< 800px`

开发工作区内部使用：

```text
代码与 Agent｜测试
```

该 Tab 只是窄屏布局降级，不恢复全局「开发／调试」分割。

Toolkit 验证矩阵在窄屏下改为纵向卡片，不压缩为不可读表格。

## 十五、安全与交互边界

1. 用户界面不得出现内部组件名称，只使用「WeWorker 网站探索」「网站探索 agent」和「Agent 浏览器」。
2. 页面、日志、Evidence 和 Tooltip 不展示模型 Key、内部 token、原始 `target_id` 或 CDP URL。
3. 人工代码和 Agent 代码使用同一运行与信任边界，本设计不新增独立代码沙箱。
4. 服务端 Slot 校验和 Debug Run 是应用资格的最终边界，前端按钮禁用不能替代服务端复核。
5. 所有确认弹窗只能通过明确取消／关闭控件或提交成功关闭，不响应遮罩点击或 `Escape`。
6. 不为运行详情增加未经脱敏的 stdout、stderr、网络、CDP 或环境变量输出。
7. 不自动执行可能产生网页副作用的测试。

## 十六、实施顺序

1. 将本设计中的产品规则同步到 Toolkit 产品设计和技术设计。
2. 修订现有前端 UI 设计，将工作区改为「探索｜开发｜Toolkit 验证」。
3. 增加人工保存开发中代码的后端接口、哈希冲突和活动互斥校验。
4. 增加代码编辑、保存、取消和未保存草稿保护。
5. 将 development Debug 嵌入开发工作区右侧。
6. 增加失败 Debug Run 的显式 Evidence 绑定。
7. 将用户界面的「发布」替换为「应用到 Toolkit」。
8. 新建 Toolkit 验证工作区并迁移 formal Debug。
9. 将多 Tool 组合验证接入 Toolkit 验证工作区。
10. 完成自动化、真实浏览器和响应式验收后更新 Roadmap。

实施过程中必须保持每一步可独立验证，不把编辑器、工作区迁移、人工保存 API、正式验证和多 Tool 执行链一次性混成不可定位的大改动。

## 十七、验证标准

### 17.1 自动化

- 三个工作区按「探索｜开发｜Toolkit 验证」排列。
- Tool 与 Toolkit 作用域切换规则正确。
- 用户可以编辑并保存开发中 Python 代码。
- 已应用代码始终只读。
- 参数签名与 Schema 不一致时保存失败。
- `expected_code_hash` 冲突不会覆盖服务端新版本。
- 存在未保存草稿时不能测试、提交 Agent 或离开而不提示。
- 人工或 Agent 修改后，旧成功测试不能解锁应用。
- 当前代码哈希测试成功后「应用到 Toolkit」解锁。
- 未验证提示和成功 Toast 使用固定文案。
- 应用成功后开发中槽位清空，已应用代码更新。
- 失败 Run 只有用户点击后才成为 Agent 证据。
- Evidence 经过脱敏且旧哈希状态可见。
- formal Debug 只在 Toolkit 验证中承担正式资格。
- 正式产物哈希变化后 Toolkit 验证矩阵正确失效或保留证据。
- 导出和安装严格依赖当前 Toolkit 验证资格。
- 页面不出现内部组件名称。

### 17.2 构建与语法

- 修改的前端 JavaScript 通过语法检查。
- Server 和 Store 聚焦测试通过。
- 组件完整测试通过。
- WeWorker embedded 集成回归通过。
- Renderer 正式构建通过。
- `git diff --check` 通过。

### 17.3 手动验收

- 完成「人工修改 → 保存 → 测试 → 应用到 Toolkit」闭环。
- 完成「测试失败 → 作为修复依据 → Agent 修改 → 再测试」闭环。
- 完成「应用到 Toolkit → 正式验证 → 导出资格更新」闭环。
- 完成「正式验证失败 → 基于此结果继续修改」闭环。
- 宽屏双栏、普通窗口抽屉和窄屏内部 Tab 均无横向溢出。
- 全局活动运行时所有冲突操作禁用且原因准确。
- Tool 定义抽屉、确认弹窗和截图灯箱只能通过明确控件关闭。

## 十八、验收后的产品结果

改造完成后，用户在开发工作区内即可完成：

```text
查看代码
→ 手动修改或让 Agent 修改
→ 运行测试
→ 将失败结果作为修复依据
→ 再次修改和测试
→ 应用到 Toolkit
```

只有进入真实交付验证时，用户才切换到 Toolkit 验证工作区：

```text
验证已应用代码
→ 验证多 Tool 组合
→ 满足导出资格
→ 导出或安装
```

这使三工作区分别对应证据采集、Tool 开发、Toolkit 交付验证，不再按照后端 Run 类型机械切割用户流程。
